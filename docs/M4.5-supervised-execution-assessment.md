# M4.5 — avaliação de execução textual supervisionada

## Decisão

Esta etapa não habilita execução real de agentes. Nenhum dos dois fornecedores oferece, pela integração disponível neste repositório, todos os controles verificáveis exigidos ao mesmo tempo: isolamento descartável com diretórios explicitamente limitados, bloqueio de ferramentas e escalonamentos, acesso externo restrito ao serviço do modelo, cancelamento confiável e limites rígidos de tempo e saída. Adicionar um executor antes de resolver esses pontos criaria uma promessa de isolamento que os contratos atuais não garantem.

Os adaptadores Codex e Gemini continuam servindo apenas para cadastro, autenticação/verificação e diagnóstico. O `MaestroCoordinator` e o contrato `AgentExecutor` permanecem inalterados. O resultado M4.5 é este relatório e testes de regressão que asseguram o bloqueio por padrão; não há componente de execução experimental.

## Codex — SDK Python oficial

- **Execução textual:** o SDK oficial expõe `Codex.thread_start(...)` e `Thread.run(texto)`. O fluxo poderia consultar `account()` antes da solicitação.
- **Permissões:** a aplicação pode exigir `agent.execute` e `web.access` em concessões explícitas. A verificação de conta existente exige `web.access`; o Maestro exige `agent.execute`. A associação de agente/provedor não concede nenhuma delas.
- **Aprovações:** a API pública atual oferece `ApprovalMode.deny_all`, que mapeia pedidos de aprovação para `never`, e `ApprovalMode.auto_review`. Um executor experimental teria de fixar `deny_all` ao criar a thread e ao iniciar o turno; não poderia usar o cliente `CodexClient` de baixo nível com o handler padrão, pois versões documentadas podem aprovar automaticamente pedidos de execução/alteração.
- **Arquivos, ferramentas e diretórios:** `Sandbox.read_only` impede gravações pela sandbox, mas a documentação do Codex descreve o modelo Windows legado como leitura completa do sistema de arquivos. `cwd` seleciona o diretório de trabalho, não estabelece uma fronteira de leitura. A sandbox não equivale a uma VM descartável nem impede que dados acessíveis sejam incluídos em uma resposta transmitida ao modelo.
- **Comandos e escalonamento:** `deny_all` bloqueia solicitações de aprovação/escalonamento, e `read_only` limita gravações. Isso não desabilita de forma comprovada todas as ferramentas; comandos que não exijam aprovação ainda podem ser considerados dentro do perfil e a leitura de disco permanece ampla.
- **Rede:** a chamada ao modelo exige rede. A política de rede de execução de ferramentas não é uma garantia de rede restrita ao endpoint do modelo para todo o processo SDK.
- **Cancelamento e limites:** `Thread.turn()` retorna um handle que oferece `interrupt()`, então existe cancelamento cooperativo documentado. A API de conveniência `run()` não expõe timeout ou limite de tamanho. Um wrapper poderia impor um prazo e limitar texto coletado via streaming, mas o SDK não documenta limite rígido de memória/saída de resposta no servidor.
- **Garantido vs. instrução:** as opções de sandbox e aprovação são configurações da execução, não texto do prompt. Instruções pedindo “somente responder” não bloqueiam ferramentas. Mesmo com os modos seguros fixados, não há confinamento de leitura Windows ao diretório descartável exigido aqui.

**Impedimento para implementação:** a garantia de isolamento de dados pessoais não está presente no SDK público Windows usado pelo projeto. A conexão Codex autenticada também reutiliza a sessão local; movê-la para uma VM isolada exige login ali, mas não resolve por si a política de leitura/rede.

## Gemini CLI oficial

- **Execução textual:** a CLI documenta modo headless com `gemini -p "pergunta"`.
- **Permissões e aprovação:** o modo `default` pede confirmação para ferramentas mutáveis em sessão interativa. O modo `auto_edit` aprova ferramentas de edição; `yolo` aprova tudo. O modo `plan` é descrito como somente leitura, mas a própria documentação diz que ainda está em desenvolvimento e não é plenamente funcional. Não há aprovação humana da aplicação no modo headless que possa ser tratada como autorização confiável.
- **Ferramentas:** a CLI dispõe de ferramentas para shell, arquivos, web e extensões/MCP. Políticas podem restringir ferramentas, mas configuração existente do usuário, diretório confiável, extensões e futuras mudanças na CLI influenciam o comportamento. O modo textual não é um endpoint de texto sem ferramentas comprovado por este adaptador.
- **Sandbox/diretórios:** o sandbox Docker/Podman isola ferramentas em contêiner, mas monta o diretório atual no mesmo caminho e permite alterações no workspace. Um diretório temporário descartável reduziria o impacto local, mas o processo da CLI continua no host e o conjunto de dados montados/configuração de autenticação deve ser avaliado. O sandbox nativo Windows usa mudanças de integridade que podem persistir após a sessão. Nenhum desses fluxos está atualmente integrado ou validado pelo projeto para isolamento descartável e estritamente somente leitura.
- **Rede:** Docker/Podman permite configurar a rede, mas a CLI precisa alcançar o serviço Gemini; desativar a rede também interrompe a chamada ao modelo. O processo host ainda necessita autenticação e rede. A configuração documentada não oferece a este adaptador uma prova de que o tráfego de saída é limitado ao endpoint necessário.
- **Cancelamento e limites:** uma execução headless poderia ser encerrada pelo processo pai; a CLI não fornece atualmente uma porta de cancelamento/timeout integrada ao `AgentExecutor` deste projeto. O tamanho máximo de saída teria de ser imposto pelo wrapper e pelo controle do processo.
- **Autenticação verificável:** a integração atual não inspeciona arquivos de sessão nem tenta chamar o modelo para inferir login; a conta permanece não verificada.
- **Garantido vs. instrução:** prompt textual e aprovação `plan` não podem ser tratados como fronteiras de segurança. O único uso aceitável futuro precisa bloquear de fato ferramentas e extensões, controlar diretórios e rede fora das instruções do modelo e terminar o processo de forma verificável.

## Alternativas para reavaliação

1. Avaliar uma execução em VM descartável controlada pela aplicação, sem diretórios pessoais montados, sem credenciais do host e com rede de saída controlada para o fornecedor; autenticar de forma oficial dentro dessa VM.
2. Avaliar o SDK Codex novamente quando a API pública permitir declarar raízes de leitura exatas e controles por ferramenta sem escalonamento, ou quando houver uma política Windows suportada que demonstre essas propriedades.
3. Avaliar Gemini CLI novamente quando a execução headless oferecer lista de ferramentas efetivamente desabilitadas, políticas não contornáveis por configuração do usuário e sandbox Windows com diretórios/rede estritamente declarativos.

Essas são condições para nova análise, não implementações nem recomendações para contornar políticas do fornecedor.

## Único teste real opcional

Não execute este teste pelo Agente Pessoal: ainda não existe executor de provedor conectado ao Maestro. Quando o usuário decidir testar a capacidade de resposta do Codex separadamente, o teste manual mínimo deve ocorrer dentro de uma VM descartável (por exemplo, Windows Sandbox) sem pastas do host mapeadas; autentique oficialmente dentro da VM e faça uma única chamada de texto com `ApprovalMode.deny_all` e `Sandbox.read_only`, usando como pergunta: **“Responda somente: teste de texto M4.5 OK.”** Não peça leitura, comandos, ferramentas ou arquivos. Confirme que a resposta é recebida e encerre a VM. A chamada requer autorização explícita do usuário no momento do teste; não foi realizada como parte desta entrega.
